# 身份认证与数据权限

DocBase 的安全模型由“身份认证、功能权限、资源归属、知识数据权限”四层组成。页面隐藏按钮只改善交互，真正的授权判断始终在 Gateway、业务服务和检索链路中执行。

## 身份认证

用户登录后获得短期访问令牌和可轮换的刷新令牌。访问令牌由 IAM 签发，各业务服务独立验签并读取用户 ID、组织 ID、管理员标记和权限集合。

- Gateway 会删除客户端伪造的 `X-User-*` 身份头。
- 业务服务不信任浏览器传入的用户 ID，而是从已验证的 Principal 获取身份。
- 注销、密码重置、用户状态或组织变化会更新授权版本，使旧令牌失效。
- 刷新令牌轮换后旧令牌立即失效，降低长期凭证泄露风险。
- 首个超级管理员使用部署侧初始化密钥创建；普通注册只能获得预设的最小权限角色。

## RBAC 功能权限

IAM 采用“用户—角色—菜单/按钮”关系计算权限字符串，例如：

- `system:user:list`：查看用户；
- `knowledge:document:create`：上传文档；
- `ingest:task:retry`：重试导入任务；
- `ai:chat:query`：发起 AI 问答；
- `admin:all`：超级管理员权限。

Controller 使用方法级授权校验权限。前端根据同一权限集合展示菜单和操作入口，但前端状态不能替代后端校验。

## 菜单授权与管理归属

菜单存在两种独立关系：

| 关系 | 数据表 | 含义 |
| --- | --- | --- |
| 角色菜单授权 | `sys_role_menu` | 角色成员能看到菜单并获得对应 permission |
| 菜单管理归属 | `sys_menu_owner_role` | 角色成员有权维护该菜单资源 |

设置 Owner 不会授予 permission，分配菜单权限也不会自动成为 Owner。普通管理员执行创建、更新、移动、启停和删除时，需要同时满足资源归属与权限边界；超级管理员可以通过 Owner 接口完成转让。

角色停用或删除前会检查其是否仍是某个菜单的唯一有效 Owner。若是，系统返回 `ROLE_LAST_MENU_OWNER`，要求先完成归属转让，防止菜单成为无人可管理资源。

Owner 替换、角色停用、角色删除和菜单 Owner 继承使用数据库守卫行串行化，避免多实例并发下出现最后 Owner 丢失或孤儿关系。

## 知识库可见范围

知识库和文档支持公开、组织内和私有范围，并叠加知识库成员角色：

| 场景 | 可见条件 |
| --- | --- |
| 公开内容 | 具有相应功能权限的用户可访问 |
| 组织内容 | 用户与内容的组织快照一致 |
| 私有内容 | 用户是知识库成员或超级管理员 |
| 历史空组织数据 | 默认拒绝组织范围匹配，避免升级后扩大权限 |

知识库成员角色按 OWNER、ADMIN、EDITOR、VIEWER 控制资源操作。功能权限决定“能否调用某类接口”，成员角色和可见范围决定“能否操作这一个知识库或文档”。

## 权限下沉到检索层

AI 问答不会只依赖页面上的知识库选择：

1. Chat 携带当前用户 JWT 向 Knowledge 查询可见文档 ID。
2. Knowledge 根据组织、公开范围和成员关系计算结果。
3. Chat 将服务端得到的文档集合传给 RAG。
4. RAG 在向量召回时过滤文档，未授权 Chunk 不会进入排序、Prompt 或引用。

这条链路防止用户通过伪造请求、猜测文档 ID 或绕过前端，将无权限内容带入大模型上下文。

## 部署安全建议

- `.env` 不得提交到 Git；生产环境应使用专用 Secret 管理系统。
- JWT 密钥、内部 API Key、数据库密码和对象存储凭证应分别随机生成。
- 内部服务接口只在容器网络开放，不映射不必要的宿主机端口。
- 不在日志中输出 Token、密码、完整 Prompt、对象 Key 或原始文档内容。
- 正式环境应关闭自助注册或明确配置默认角色和组织分配流程。
